## 2. 灰度回滚（A15）

**结果：通过（同一 schema 版本内）。**

前置：确认 `generation_runs` 无占用名额（`capacity_held=TRUE` 为 0），因此切换不会影响运行中的任务；备份 `compose.yml`、`nginx.conf`、`Dockerfile`、`api.env` 与全库 dump 到 `/data/backup/huimeng/a15-20261027-134920/`（1.4 MB，`gzip -t` 通过）。

| 步骤 | 动作 | 实测 |
| --- | --- | --- |
| 基线 | 当前 `huimeng-api:m3`（`892cbd2b4872`） | 项目 10、素材 9 / 15 011 684 B、视频 sha 一致、节点 8、工具 1、审计 214 |
| 回滚 | 用上一版 JAR 重建 `huimeng-api:prev-m3`（`c9d00b4aa1ae`），`HM_IMAGE=… compose up -d --force-recreate api` | 启动 **4.766 秒**；CSRF/登录 200；项目 10、素材 9 / 15 011 684 B、视频 sha 一致、节点 8、工具 1 |
| 正向 | 切回 `huimeng-api:m3` | 启动 3.5 秒；上述指标完全一致 |
| 数据库 | 回滚前后 `projects 10 / media 10 / media_bytes 16 676 315` | 不变（audit 214→216 为两次健康检查的登录审计） |

证据：[m4-a15-rollback-20261027.json](evidence/m4-a15-rollback-20261027.json)。

**边界（重要）**：本次演练的两版都处于 Flyway V10。当天后续为修复外部入口缺陷新增了 V11，此时再把旧 JAR 拉起来会被 API 的迁移校验拦下：`FlywayValidateException: Detected resolved migration not applied to database: 11`。因此运维口径是：

- **同 schema 版本内**：换镜像即可回滚（本次已实测）；
- **跨迁移版本**：必须先恢复配套数据库（`mysqldump` 已在每次发布前落盘），不能只换 JAR；
- 迁移必须由 `--profile migration` 的 migration 容器执行，API 只做校验、不自行迁移。

用 `huimeng-api:m2`（V3 时代）对 V10 库做过一次 `--migrate-only` 探测：Flyway 仅告警「schema 版本 10 高于本地最新 3」并正常退出，数据库未被改动；但这只是迁移检查，**未**把 m2 作为线上版本切换验证。

## 3. Web / MCP / A2A 混合并发

**结果：部分通过。** Web 与 MCP 的共享名额、隔离、取消、异常传播、结果完整性均实测通过；A2A 因产品设计（只跑文本智能体）与环境缺口（未配置文本供应商）未参与媒体名额。

| 验证点 | 实测 | 结论 |
| --- | --- | --- |
| 并发执行 | 同一项目同时发起 Web×2 + MCP×2 + Web×1，5 个全部 200 并最终 SUCCEEDED；耗时 153.6 / 254.3 / 202.0 秒（Web 三路）与即时返回（MCP 两路异步） | 通过 |
| 共享名额 | 5 个占用期间，第 6 个经 **MCP** 入口发出 → **429** `PROJECT_CAPACITY_EXCEEDED`，**0.04 秒**返回，未触达执行器 | 通过 |
| 异项目独立计数 | 另一项目在 Alpha 占满 5 个时仍被接受并成功 | 通过 |
| 任务隔离 | Beta 客户端 `getRun(Alpha 运行 ID)` → `运行不可用`（isError），看不到他人运行 | 通过 |
| 取消/超时路径 | 生成中取消：202 → `CANCELLED`，10.1 秒收敛，素材数不变（19→19），名额释放 | 通过 |
| 异常传播 | A2A 缺 `A2A-Version` → 400 `VERSION_NOT_SUPPORTED`；第 6 个 → JSON-RPC `-32099` + `PROJECT_CAPACITY_EXCEEDED` | 通过 |
| 结果完整性 | 本轮 5 个媒体逐一下载，sha256 全部与库内一致 | 通过 |
| **A2A 参与同一计数** | A2A `SendMessage` 可建任务，但任务终态 `TASK_STATE_REJECTED`「团队尚未启用文本模型」 | **不适用/未通过** |

**为什么 A2A 不参与名额**：`/a2a/{team}` 走的是智能体文本任务（`agents.generate`），不调用媒体执行器；它没有 `generateMedia` 这类工具入口（那是 MCP 的）。因此「Web+MCP+A2A 三家抢同一组 5 个媒体名额」在现有设计下无法成立；能成立的是「三者并发访问同一项目时互不干扰、各自的状态与隔离正确」，这一点已验证。

证据：[m4-mixed-concurrency-20261027.json](evidence/m4-mixed-concurrency-20261027.json)。

**本轮修掉的阻塞缺陷**：MCP 入口的 `generateMedia` 原本 100% 失败——见第 6 节 D1。修复前该入口在真实部署上从未成功过。

## 5. 本轮缺陷清单

| 编号 | 缺陷 | 影响 | 处理 |
| --- | --- | --- | --- |
| D1 | `project_media.created_by` 有指向 `users` 的外键，但外部客户端（MCP/A2A）用自己的客户端 id 作为 actor | **所有外部入口的媒体生成在最后入库时失败**；运行走到「上游已完成」后变 FAILED，产物被丢弃 | 新增 `V11__RelaxProjectMediaCreatorFk`（Java 迁移，按方言查约束名后删除外键、保留索引）；新增用例 `mediaCreatorAcceptsExternalClientIds`。修复后 MCP 生成实测 SUCCEEDED |
| D2 | 媒体生成失败被完全吞掉：无日志、`RunRespDTO` 不带原因 | 线上只能看到「生成失败，请稍后重试」，无法定位；D1 藏了很久 | 两处 catch 增加 WARN（run id、remoteAttempted、confirmed、异常类型与消息，不含提示词/凭据）；用户主动取消（`CANCELLED`）不计入失败日志，避免失败率统计失真 |
| D3 | 素材预览只支持图片，mp4 提示「请下载后查看」 | 视频结果无法在页面内确认 | 前端补视频内联播放（128 MiB 上限） |
| D4 | 部署脚本先清空 `/var/www/huimeng` 再解压，而 `upload/` 目录已被清理导致解压失败 | 站点出现短暂空白（已立即用备份恢复） | 恢复站点；发布流程改为「先确认上传成功再清理站点」，见服务器规范 |

## 6. 未修复与未覆盖

**未修复（不阻塞签收，但需排期）**

1. `generation_runs.kind` 对视频运行也写 `'image'`（`GenerationRunMapper.insert` 里是字面量）。不影响状态机与产物，但按类型统计会失真。
2. `RunRespDTO` 目前不返回失败原因（只有 state）。D2 的日志只解决运维侧定位，客户端仍拿不到原因；建议下一步在运行响应里加一个受控的 `reason` 字段。

**环境缺口**

3. 服务器没有配置任何文本模型密钥（`provider_secrets` 为空，`deepseek/qwen` 均 `enabled=0`），因此 A2A 任务全部 `TASK_STATE_REJECTED`，Agent 文本生成同样不可用。这属于部署配置缺口，不是代码缺陷。
4. 生产库未启用任何 `h3Local3060/*` 模型（本轮为验收临时启用后已恢复）；要正式提供视频能力需要产品决定常开哪些模式。

**未覆盖**

5. 真实 Web/MCP/A2A **用户级**并发规模只做到 5（受单卡 12 GB 限制，ComfyUI 串行执行）；更高并发下的排队时延与失败率未测。
6. 跨迁移版本回滚只验证了「会被拦下」，未做「恢复数据库后回滚」的完整演练。
7. MCP/A2A 的页面控制桥（画布操作）仍只有夹具证据，未在真实部署上重跑。
