# 本地媒体执行器的串行派发与时限

> 状态：已实现（2026-10-27）。适用于 `qwenImage21Local` 与 `h3Local3060` 两个本地 ComfyUI 供应商。

## 1. 为什么串行

现用执行器只有一张 12GB 显卡。多个生成任务同时提交时，ComfyUI 会在 Qwen Image 与 MiniMax H3 之间反复换入换出模型，单张图片的耗时从约 66 秒涨到 831 秒，视频任务也会被拖慢。平台侧必须保证**同一时刻只有一个任务真正提交给执行器**。

串行只发生在执行器边界，不改变用户看到的并发语义：

- 每个请求仍各自持有一条 HTTP 流，受理后立即返回 `X-Run-Id`；
- 排队期间服务端每秒向流写一个空白心跳，前端持续显示“排队或生成中”；
- 请求按到达顺序（FIFO）获得执行权，不插队、不因后到而丢弃；
- 每个项目的五个名额仍然在受理时原子占用，排队中的运行也计入名额。

## 2. 请求生命周期

```
受理（校验/幂等/名额） → 取号排队 → 取得执行权 → 提交 ComfyUI → 轮询 → 下载 → 入库 → 终态
                                   ↑
                         每秒检查取消、排队超时、写心跳
```

| 阶段 | 行为 | 失败/取消 |
| --- | --- | --- |
| 受理 | 校验模型授权、参考图归属、幂等键；项目行锁内检查五个名额 | 第 6 个立即 429 `PROJECT_CAPACITY_EXCEEDED`，不进入队列 |
| 探测 | 确认执行器与对象存储可达 | 立即释放名额，`MODEL_UNAVAILABLE` / `EXECUTION_STORAGE_UNAVAILABLE` |
| 排队 | `MediaSerialGate` 票号 FIFO；每秒心跳并检查 `CANCELLING` | 用户取消 → `CANCELLED`；超过排队上限 → `FAILED` + `EXECUTION_BUSY` |
| 执行 | 只有队首能取得执行权；`finally` 必定 `release()` | 取消/超时/异常都不会把队列堵死 |
| 提交后 | 以执行器任务 ID 轮询 `/history`，按媒体类型使用各自客户端 | 超时先 `cancel`，未确认终态记 `LOST` 并保留名额等核对 |
| 入库 | 产物写入对象存储并登记 `project_media` | 入库失败记 `EXECUTION_STORAGE_UNAVAILABLE`，不伪装成模型失败 |

排队等待**不计入**生成时限，也不释放名额；只有用户取消或排队超时才结束。

## 3. 时限模型

关键区分：**单次 HTTP 调用超时**约束的是一次请求/响应交换，**不是**整段生成时间。视频生成 30 分钟以上时，轮询仍是每 2 秒一次短请求，不会被单次超时掐断。

| 配置项 | 默认值 | 约束对象 |
| --- | --- | --- |
| `huimeng.comfy.queue-timeout-seconds` | 3600（1 小时） | 从取号到取得执行权的最长排队 |
| `huimeng.comfy.image-deadline-seconds` | 1800（30 分钟） | 图片提交后到终态的总生成时间 |
| `huimeng.comfy.video-deadline-seconds` | 5400（90 分钟） | 视频提交后到终态的总生成时间，覆盖 15 秒视频跑 30 分钟以上的情况 |
| `huimeng.comfy.stream-timeout-millis` | 10800000（3 小时） | 单条流式 HTTP 连接的总时长（排队 + 生成） |
| 图片单次调用 | JSON 20 秒；上传/下载 60 秒 | 单次请求/响应交换 |
| 视频单次调用 | 提交/查询 120 秒；下载 180 秒 | 单次请求/响应交换 |

图片客户端改用 `BodyHandlers.ofByteArray()`：`HttpRequest.timeout` 只保证响应头到达，`ofInputStream` 之后的正文读取不受超时约束；改成字节数组后，单次超时覆盖整个响应体，避免执行器“发完响应头就不再吐字节”把线程永久挂住。所有响应体仍有大小上限（JSON 1 MiB、图片 16 MiB、视频按执行器产物校验）。

生成时限到达时先调用执行器取消接口，再抛 `MODEL_TIMEOUT`；由于已提交但未确认终态，运行记为 `LOST` 并保留名额，由每 10 秒一次的核对任务在拿到终态后释放；超过 30 分钟仍查不到终态则强制释放，防止名额永久泄漏。

## 4. 配置与部署

默认值写在代码里，部署时可用环境变量覆盖：

```bash
HUIMENG_COMFY_QUEUE_TIMEOUT_SECONDS=3600
HUIMENG_COMFY_IMAGE_DEADLINE_SECONDS=1800
HUIMENG_COMFY_VIDEO_DEADLINE_SECONDS=5400
HUIMENG_COMFY_STREAM_TIMEOUT_MILLIS=10800000
```

调大视频时限会同时拉长单条 HTTP 连接；反向代理的读超时必须不小于 `stream-timeout-millis`，否则前端会先被代理断开。

## 5. 验收口径

- 两个请求同时提交：两个都受理并拿到运行号；执行器侧最大并发为 1；先到者结束后后者才开始。
- 排队中取消：运行进入 `CANCELLED`，名额释放，队列中后续任务不受影响。
- 生成超过 30 分钟的视频：不因单次 HTTP 超时失败；90 分钟总时限内完成即成功。
- 执行器不可达：受理后立即释放名额，返回受控 `MODEL_UNAVAILABLE`，不留下 `LOST` 占位。
- 进程重启：未提交到上游的运行立即释放；已提交的运行进入 `LOST`，由核对任务收敛。

## 6. 已知边界

- **重启时的孤儿任务**：API 重启后本地队列为空，但 ComfyUI 可能仍在跑重启前的任务。此时新任务会进入 ComfyUI 自己的队列，通常仍按执行器顺序执行，但平台侧无法感知那段占用。生成高峰期应避免滚动重启。
- **客户端断开不等于取消**：浏览器关闭不会释放名额，运行会继续到终态并入库；用户可在运行查询页看到结果。这是既有约定（名额属于项目，不随浏览器断线释放）。
- **单实例假设**：串行闸门是进程内状态。1.0 只部署一个 API 实例；若将来水平扩容，需要把闸门改为数据库或分布式锁，否则多实例会各自向执行器提交。
- **排队超时是保护而非故障**：执行器长期卡住时，后来者会在 1 小时后收到 `EXECUTION_BUSY`，而不是无限期占用连接。
